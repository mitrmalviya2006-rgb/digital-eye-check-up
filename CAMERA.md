# Component 2 camera behavior and handoff

Camera access is requested only from the Start Camera button after Component 1 stores a completed, consented, safety-clear questionnaire in the current page session. Access uses `getUserMedia` with `audio: false`, a preferred `environment` facing mode, and centralized ideal dimensions/frame rate. If the browser rejects that preference, the controller retries once without a facing-mode constraint and reports that browser-selected camera. Device labels and identifiers stay in memory and are not logged or persisted.

The preview must reach video metadata with nonzero dimensions and successfully play before state becomes `ready`. Actual dimensions come from the video element; track capabilities and settings are read from the active track. Torch, zoom, exposure, focus, and white-balance controls appear only where `getCapabilities()` reports support. Browser/device support varies, especially for torch and manual focus. No physical-device compatibility has been assumed or asserted.

`mountCameraStep(root)` mounts the UI. It emits a bubbling `camera-step-ready` event when the user chooses Continue. The event's `detail.camera` is a controlled interface containing `getSnapshot`, `getCapabilities`, `getCurrentSettings`, `withVideoFrame(callback)`, `captureFrame()`, and `stopCamera()`. Later components should consume this interface instead of opening another stream; `withVideoFrame` provides the existing video element for active downstream processing, and `captureFrame` returns an `ImageBitmap` when supported. The `MediaStream` itself is not exposed. `questionnaire-complete` continues to carry the Component 1 result.

The controller stops all tracks on Stop, camera replacement, Back, and page exit, detaches the video element, and attempts to disable a supported torch first. Video is never uploaded or persisted. The integration is in-memory; refreshing clears questionnaire authorization and returns to Component 1.
