# Vision screening prototype

This project uses browser-native HTML, CSS, and JavaScript modules. It has no installed dependencies or bundler.

Run from the project directory with `node server.js`, then open the local URL shown in the terminal. Camera APIs require a secure context; localhost is treated as secure by modern browsers. To run verification, use `node --test` and the JavaScript syntax checks in `package.json`'s `check` script (or run `node --check` on the files listed there if npm is unavailable).

Component 1 keeps questionnaire authorization only in memory. Component 2's camera behavior and downstream interface are documented in [CAMERA.md](./CAMERA.md); questionnaire storage behavior is documented in [PRIVACY.md](./PRIVACY.md).

Component 3 uses MediaPipe Face Landmarker for local guided positioning. A live internet connection is needed to download its version-pinned runtime and model. Component 4 reuses that same worker to localize eye contours and iris boundaries; it does not detect pupils or expose per-eye confidence/occlusion. See [POSITIONING.md](./POSITIONING.md) and [EYE-LOCALIZATION.md](./EYE-LOCALIZATION.md).

Component 5 reuses the active video element and Component 4's latest eye geometry. After a separate local-processing assent, it samples a reduced in-memory frame about every 750 ms; it does not start a camera, detector, or network upload. It emits `image-quality-update` with a machine-readable `valid`/`overallStatus` contract for downstream components. The current face model has no per-eye confidence or occlusion signal, so technically clear frames remain `UNKNOWN` and are not capture-ready until those signals exist. See [QUALITY.md](./QUALITY.md) and [PRIVACY.md](./PRIVACY.md).

Component 6 reuses the same preview, positioning snapshot, eye results, and quality results. After a separate capture assent, it requires fresh accepted results, stable positioning/tracking, two distinct good quality samples, and 900 ms of continuous eligibility before extracting a full-resolution PNG frame. The captured frame is rechecked before `eye-capture-ready` and `eye-capture-complete` events are emitted. The current Component 4 model's unavailable confidence/occlusion scores keep Component 5 invalid, so this implementation intentionally remains fail-closed and cannot capture until trusted signals are provided. See [CAPTURE.md](./CAPTURE.md) and [PRIVACY.md](./PRIVACY.md).


Component 7 consumes the validated Component 6 batch, separates right/OD and left/OS crops using unmirrored eye metadata, and emits configurable typed pixel arrays through `eye-preprocessing-ready` and `eye-preprocessing-complete`. No downstream trained model is present, so defaults leave native crop dimensions and raw RGB byte values unchanged; model-specific resize, layout, color mode, and normalization are configuration options rather than guessed requirements. See [PREPROCESSING.md](./PREPROCESSING.md).

Component 8 consumes that preprocessed batch and emits versioned, per-eye landmark geometry and iris-boundary pixel statistics through `eye-features-ready` and `eye-features-complete`. Its fixed feature order and model-specific vector adapter never fill missing values or infer pupil geometry. No Component 9 model exists, and the feature vectors are explicitly marked not model-ready. See [FEATURE-EXTRACTION.md](./FEATURE-EXTRACTION.md).

Component 9 now provides a fail-closed local model-inference boundary, versioned output contract, and app handoff. The repository contains no trained refraction model or ML runtime, so the default state reports the model unavailable and emits no SPH/CYL/Axis values. A future model must bring its documented manifest, artifact metadata, local adapter, and exact output decoder. See [PREDICTION.md](./PREDICTION.md).

Component 10 validates C9's explicit OD/right and OS/left prediction records, groups each source prediction by eye without averaging, and exposes a UI-independent handoff for later reliability review and display. Missing/failed eyes remain explicit and no values are shown in the C10 screen. See [EYE-ANALYSIS.md](./EYE-ANALYSIS.md).

Component 11 consumes that C10 handoff, checks model-declared values and reliability, image-quality/localization evidence, capture stability, and repeated-prediction consistency, then emits `eye-validity-complete` and `eye-consistency-assessment`. Its configurable policy is in `src/config.js`; unsupported thresholds remain unset so the engine fails closed. See [VALIDITY.md](./VALIDITY.md).

Component 12 consumes the Component 13 pass gate and preserves each accepted OD/OS measurement separately; it withholds values on uncertain/failed outcomes. It emits `prescription-result-ready` for future history/PDF consumers and `component13-retest-request` for retest requests. See [RESULT-SCREEN.md](./RESULT-SCREEN.md).

Component 13 records image-free Component 11 outcomes, handles terminal Component 6 capture failures, bounds retries, and compares each eye's SPH/CYL/Axis only against configured per-parameter tolerances. Retests return to the existing Component 2 setup and reuse Components 3–9; there is no duplicate camera or inference pipeline. Values remain separate and are never averaged. `RETEST_POLICY` in `src/config.js` sets a technical retry cap of 2; consistency tolerances remain unset until documented model/system limits are available, so repeated readings cannot pass consistency unassessed. The component exposes `component13-retest-result-ready` and the existing C12 `prescription-result-ready` event supports future Components 14/15. See [RETEST.md](./RETEST.md).

Component 14 displays final C12 results through Component 16's local history API. Results are saved only when the user opts in; invalid/retest-failed sessions remain labeled with estimates withheld. History includes view, confirmed delete, PDF export, session reset, and local-data deletion. See [HISTORY.md](./HISTORY.md).

Component 15 creates local PDF reports from the exact C12/C14 result data, and Component 16 centralizes result history, minimal consent receipts, settings, session state, availability checks, export, reset, and deletion. It uses the existing IndexedDB database upgraded from schema v1 to v2, preserving old result records. Questionnaire answers and active camera/session data remain memory-only; image/frame data is excluded from persistence. Component 17 can use the C16 `getStorageAvailability()` API rather than probing storage directly. See [DATA-PRIVACY.md](./DATA-PRIVACY.md).

Component 17 checks secure-context/browser APIs before asking for camera permission and reconciles camera, torch, rear-facing mode, resolution, frame rate, controls, compute, performance hints, and Component 16 storage from actual API evidence. It configures only browser-supported camera constraints, keeps captured frames at native resolution, and adjusts processing cadence only from advisory device-resource hints. Component 9 has no configured model runtime, so compatibility does not pretend a prediction engine is available. See [DEVICE-COMPATIBILITY.md](./DEVICE-COMPATIBILITY.md).
